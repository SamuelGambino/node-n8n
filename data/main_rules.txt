1. Правила формирования полей report
client_id : Идентификатор текущего/последнего проекта в цепочке projects_history, объединяющей старые и новые project_id одного клиента
project_ids: Все project_id, относящиеся к одной такой цепочке, в хронологическом порядке, например 310|311
project_name: Название проекта, актуальное на начало конкретного флайта
service_type: Услуга, актуальная на начало конкретного флайта с учётом service_changes
term_months: Длина флайта для соответствующего service_type из service_terms
flight_no: Порядковый номер флайта внутри клиентской истории: 1, 2, 3...
flight_start: Первый месяц флайта
flight_end: Последний месяц флайта по его term_months
last_active_month: Последний месяц в пределах флайта, в котором была фактическая отгрузка (amount > 0)
status: Вычисляется по фактической активности, событиям (label), наличию следующего флайта, типу проекта и report_generated_at
report_generated_at: Дата, на которую строится отчёт; для проверки старого отчёта нельзя использовать данные works, появившиеся после этой даты
2. Самая важная сущность — клиентская история
Программа должна сначала превратить отдельные проекты в цепочки одного клиента.
Например:
310 → 311
означает:
client:
  310
  └── с 2024-07 → 311
Поэтому:
client_id = 311
project_ids = 310|311
Но:
2024-01 → 2024-06
project_id = 310
project_name = Гамма Ритейл

2024-07 → 2024-12
project_id = 311
project_name = Гамма Ритейл Про
Это надо сделать до формирования флайтов.
3. Как должна работать Node.js-программа
Я бы разбил её на такие этапы:
CSV files
   ↓
1. Загрузка и нормализация
   ↓
2. Построение справочников
   ↓
3. Построение истории клиентов
   ↓
4. Восстановление временных атрибутов
   ↓
5. Формирование флайтов
   ↓
6. Расчёт last_active_month
   ↓
7. Расчёт status
   ↓
8. Формирование expected report
   ↓
9. Сравнение expected report ↔️ report.csv
   ↓
10. report_fixed.csv
   ↓
11. AUDIT / discrepancies
4. Этап 1 — загрузка
Все CSV преобразуются в массивы объектов:
works[]
projects[]
projectsHistory[]
serviceChanges[]
serviceTerms[]
report[]
Сразу нормализовать:
month → Date / YYYY-MM
amount → number
project_id → string
project_id я бы хранил именно как string, потому что это идентификатор, а не число.
5. Этап 2 — справочники
Создаются Map:
projectsById
serviceTermsByType
serviceChangesByProject
historyByProject
worksByProject
Например:
serviceTermsByType.get("Мониторинг СМИ")
// → 12
Это сильно упростит дальнейшую логику.
6. Этап 3 — построение client history
Из:
projects_history:
310 → 311
320 → 321
строим:
ClientHistory {
  clientId: "311",
  projectIds: ["310", "311"]
}
и:
ClientHistory {
  clientId: "321",
  projectIds: ["320", "321"]
}
Для проектов без history:
301 → clientId 301
302 → clientId 302
...
Важное допущение
Мы пока предполагаем:
последний new_project_id в цепочке = client_id.
Это надо отдельно проверить на всех данных.
7. Этап 4 — определить состояние проекта в каждый месяц
Это ключевой слой.
Для каждого месяца нужно знать:
ProjectState {
  projectId
  projectName
  serviceType
  termMonths
}
Например:
2024-06:
projectId = 310
projectName = Гамма Ритейл
serviceType = Управление репутацией

2024-07:
projectId = 311
projectName = Гамма Ритейл Про
serviceType = Управление репутацией
Приоритет источников
Для project_name:
projects
+ projects_history
Для service_type:
projects
+ service_changes
Для term_months:
service_type
→ service_terms
А projects.term_months использовать как контрольное значение, а не как основной источник.
То есть:
expectedTerm = serviceTermsByType.get(serviceType)

if (project.term_months !== expectedTerm) {
   flagDataConflict()
}
8. Этап 5 — формирование флайтов
Вот здесь я бы пока использовал такое правило:
Для обычного проекта
Берём непрерывную историю обслуживания клиента и разбиваем её на блоки по term_months.
Например:
6 месяцев:

Jan Feb Mar Apr May Jun
Jul Aug Sep Oct Nov Dec
получаем:
flight 1 = Jan–Jun
flight 2 = Jul–Dec
Но есть исключения
STOP должен иметь более высокий приоритет.
Например:
Jan Feb Mar Apr
STOP
Jun Jul Aug Sep
первый период считается завершённым раньше планового конца.
И здесь я бы не зашивал пока окончательное поведение для нового флайта без проверки всех данных — это один из потенциальных спорных моментов ТЗ.
9. flight_start
Просто первый месяц флайта.
Например:
flight 1 → 2024-01-01
flight 2 → 2024-07-01
10. flight_end
Для обычного флайта:
flightEnd = addMonths(flightStart, termMonths - 1)
То есть:
start = 2024-01
term = 6

end = 2024-06
Не 2024-07.
11. last_active_month
Берём все записи works внутри границ флайта:
works
  .filter(month >= flightStart && month <= flightEnd)
  .filter(amount > 0)
и берём max(month).
Например:
flight:
Jan Feb Mar Apr May Jun

works:
Jan
Feb
Mar
Apr
Получаем:
last_active_month = Apr
STOP сам по себе не является активностью, поэтому amount = 0 исключается.
12. status
Я бы не пытался сразу свести его к одной формуле. Лучше сделать decision tree.
Примерный порядок:
1. Разовый?
   → "завершился (разовые работы)"

2. STOP внутри флайта?
   → "отвал"

3. Есть следующий флайт?
   → "пролонгировано"

4. Флайт закончился давно и следующего нет?
   → "непролонгировано"

5. Флайт закончился недавно относительно report_generated_at?
   → "неизвестно"

6. Иначе?
   → нужно проверить кейс / NEEDS_REVIEW
Почему такой порядок важен:
STOP нельзя превращать в обычное непролонгировано.
13. Что делать с report_generated_at
Это надо применять до анализа данных.
Если:
report_generated_at = 2025-09-01
то для восстановления старого отчёта:
works.filter(month <= reportGeneratedAt)
То есть для 350:
2025-09
2025-10
2025-11
...
Октябрь и дальше не должны влиять на старый отчёт.
А вот при аудите текущих данных мы уже можем отдельно сказать:
В актуальных данных после даты формирования отчёта появилась дополнительная активность.
Это две разные вещи.
14. Что делать, если данные противоречат друг другу
Очень важно: не пытаться автоматически решить всё.
Например:
projects.term_months = 6
service_terms = 12
Программа должна сделать:
auditFlag = "DATA_CONFLICT"
auditComment = "..."
а не молча выбрать 6 или 12.
15. Я бы разделил внутренние сущности
Чтобы код не превратился в кашу, держи три уровня:
Raw data
  ↓
Client history
  ↓
Flights
  ↓
Report rows
Например:
type ClientHistory = {
  clientId: string;
  projectIds: string[];
};

type Flight = {
  clientId: string;
  projectId: string;
  projectName: string;
  serviceType: string;
  termMonths: number;
  flightNo: number;
  flightStart: string;
  flightEnd: string;
  lastActiveMonth: string | null;
  status: string;
};
А уже после этого Flight преобразуется в строку CSV.
16. Итого: как я бы сформулировал алгоритм
1. Загрузить CSV
2. Нормализовать даты / числа / ID
3. Построить справочники
4. Построить цепочки project_id → client_id
5. Для каждого клиента восстановить исторические состояния проектов
6. Определить периоды обслуживания
7. Разбить их на флайты по service_terms
8. Для каждого флайта:
      - project_name
      - service_type
      - term_months
      - flight_no
      - flight_start
      - flight_end
      - last_active_month
      - status
9. Сформировать expected report
10. Сравнить его с report.csv
11. Для каждой разницы определить:
      - REPORT_ERROR
      - DATA_CONFLICT
      - NEEDS_REVIEW
12. Сформировать report_fixed.csv
13. Сформировать AUDIT.md
Особенности правил построения флайтов:
1. STOP
Трактуем как досрочное аварийное завершение обслуживания.
Правило:
STOP внутри текущего флайта
→ флайт завершается в этом месяце
→ status = "отвал"
→ обязательно audit_flag / comment
Например:
flight_start = 2024-01
плановый flight_end = 2024-06
STOP = 2024-05
Получаем:
flight_end = 2024-05
status = отвал
comment = "Флайт досрочно завершён событием STOP в 2024-05."
При этом я бы не трактовал сам STOP как доказательство причины ухода. Мы знаем только, что произошло событие STOP; почему именно оно произошло — неизвестно.
2. Пропуск месяца
ожидалась регулярная отгрузка
        ↓
месяц отсутствует
        ↓
NEEDS_REVIEW
Но важно: не любой пропуск автоматически означает ошибку.
Например:
Jan Feb Mar Apr May Jun
Если May отсутствует — подозрительно.
Но если сам флайт/услуга по бизнес-логике мог начаться или закончиться в этом месте, сначала нужно учитывать границы флайта.
Поэтому я бы формулировал правило:
Пропуск ожидаемой ежемесячной активности внутри подтверждённого периода обслуживания → NEEDS_REVIEW.
3. Смена project_id
Это не новый клиент и не обязательно новый проект, а продолжение той же истории проекта с новым ID.
Например:
310 → 311
Тогда:
client_id = 311
project_ids = 310|311
Но в конкретной строке отчёта надо указывать ID, реально участвовавшие в этом флайте/месяцах.
То есть:
Jan–Jun → 310
Jul–Dec → 311
Если в одном флайте реально были одновременно:
310
311
тогда:
project_ids = 310|311
Это хороший принцип:
project_ids отражает фактически задействованные ID внутри конкретного результата, а не просто всю историю клиента.
4. Смена service_type
Здесь тоже согласен: смена услуги должна влиять на последующую логику флайтов.
Например:
до 2024-07
Крауд-маркетинг → 6 мес.

с 2024-07
Мониторинг СМИ → 12 мес.
Тогда с июля:
service_type = Мониторинг СМИ
term_months = 12
И новый флайт должен рассчитываться уже по 12 месяцам.
При этом если смена услуги произошла внутри текущего флайта, это уже сложный случай. Я бы не пытался автоматически "пересчитать задним числом" существующий флайт.
Лучше:
service_type changed inside active flight
→ NEEDS_REVIEW
→ комментарий
Потому что здесь действительно недостаточно информации о бизнес-правиле.
5. Новый флайт начался не сразу
Вот тут общий принцип:
не угадывать.
Но нужно разделить два случая.
Нормальное окончание + отсутствие продления
Jan–Jun
июль → ничего
август → ничего
...
Это вполне однозначно:
status = непролонгировано
Затем внезапно новый флайт
Jan–Jun
июль → нет
август → нет
сентябрь → есть
Вот это уже интересно.
Мы можем сказать:
Продление произошло с перерывом.
Но из ТЗ не следует однозначно, считать ли это:
новым флайтом;
поздним продлением;
новым контрактом;
отдельной услугой.
Поэтому:
NEEDS_REVIEW
и в комментарии описать фактическую ситуацию.
6. неизвестно
Я бы сделал очень конкретное правило:
flight_end близко к report_generated_at
+
ещё недостаточно времени определить продление
→ неизвестно
Но здесь лучше не придумывать самостоятельно число дней/месяцев.
Например, для 6-месячной услуги флайт закончился:
2025-08
report_generated_at = 2025-09
Мы видим, что прошло только около месяца.
Следовательно:
status = неизвестно
А если:
flight_end = 2024-06
report_generated_at = 2025-09
и ничего после июня нет:
status = непролонгировано
То есть неизвестно должно определяться относительно даты формирования отчёта, а не просто по факту отсутствия следующего флайта.
7. Я бы окончательно зафиксировал decision tree так
Для каждого флайта:
1. Разовый / сезонный
   → завершился

2. STOP внутри флайта
   → отвал
   + комментарий

3. Есть следующая непрерывная отгрузка сразу после flight_end
   → пролонгировано

4. Следующая отгрузка появилась после перерыва
   → NEEDS_REVIEW

5. Флайт закончился, и от report_generated_at прошло достаточно времени
   → непролонгировано

6. Флайт закончился недавно, и недостаточно информации
   → неизвестно

7. Внутри флайта обнаружено необъяснимое нарушение регулярности
   → NEEDS_REVIEW
И главное правило всей программы
Это принцип архитектуры:
Если программа может доказать состояние по данным — она принимает решение. Если не может — она не делает предположение, а создаёт NEEDS_REVIEW и объясняет, чего именно не хватает.
